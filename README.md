# Conventional Commits: Simplified

**Русский** | [English](README.en.md)

## Введение

Основано на [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/#спецификация)

"Соглашение о коммитах" определяет правила написания сообщений коммитов.

Перед принятием соглашения необходимо утвердить базовые принципы ведения истории коммитов:

1. **Дробление коммитов.**

   Один коммит - одно логически завершенное изменение (например, добавление новой функциональности или исправление ошибки).
   При этом важно соблюдать баланс и избегать чрезмерного дробления.

2. Каждый коммит должен представлять рабочее состояние кодовой базы, которое **компилируется без ошибок**. Если для изменяемого компонента предусмотрен запуск, он также должен **запускаться** (например, поднимать контекст приложения).

3. Если изменения связаны с задачей в Jira, имя ветки должно в точности совпадать с кодом этой задачи.

---

## Структура сообщения коммита

Сообщения коммитов должны иметь следующую структуру:

```text
[1] <тип>[(<код задачи в Jira>)][!]: <описание>

[2] [необязательное тело]
```

Рассмотрим каждый блок в отдельности:

### Заголовок

`<тип>[(<код задачи в Jira>)][!]: <описание>`

Код задачи в Jira необязателен. Если он указан, то записывается в круглых скобках сразу после типа. Для коммитов без привязки к задаче код и скобки опускаются.

Типы коммитов:

* `feat` - используется при добавлении новой функциональности;
* `fix` - используется при исправлении ошибки;
* `build` - используется при изменении сборки приложения, обновлении зависимостей;
* `refactor` - используется при изменении структуры кода без добавления или изменения функциональности;
* `ci` - используется при добавлении или изменении CI-скриптов, пайплайнов и т. д.;
* `docs` - используется при добавлении или изменении документации;
* `style` - используется при изменении форматирования кода;
* `test` - используется при добавлении или изменении тестов;
* `chore` - другие изменения, не подпадающие под остальные типы;
* `revert` - откат изменений.

Описание коммита должно быть осмысленным и соответствовать единому стилю. По возможности оно должно начинаться с глагола, характеризующего действие:
`feat: добавлено ...`, `fix: исправлены ...`, `style: изменены отступы ...` и т. д.

Если изменения нарушают обратную совместимость (breaking changes), символ `!` обязателен. Он ставится непосредственно перед двоеточием: после кода задачи в скобках, если код указан, или сразу после типа.

### Тело

`[2] [необязательное тело]`

Отделяется от заголовка одной пустой строкой.

## Примеры текстов коммитов

```text
feat(JIRATASK-123): добавлено версионирование поручений
```

```text
fix(JIRATASK-123): исправлен NPE при создании этапа проекта
```

```text
build: добавлена зависимость rsql-jpa-spring-boot-starter
```

```text
feat(JIRATASK-123)!: введен новый формат без поддержки прежнего
```

```text
feat!: введен новый формат без поддержки прежнего
```

## Возможные вопросы

1. Q: *Разве это не препятствует интенсивной разработке и быстрой итерации?*

   A: В первую очередь это препятствует быстрой неорганизованной разработке. Соглашение поможет быстрее продвигаться в долгосрочной перспективе в нескольких проектах с разными участниками за счет введения стандарта.

2. Q: *Что мне делать, если коммит соответствует более чем одному типу?*

   A: Независимые изменения следует разделять на отдельные коммиты. Если изменения логически связаны и составляют единое целое, тип коммита выбирается по их основной цели.
   Соглашение позволяет получить простую и понятную картину разработки, отраженную в истории коммитов.

3. Q: *Какие буквы использовать: строчные (lowercase) или прописные (uppercase)?*

   A: В тексте коммита используются строчные буквы, за исключением имен и идентификаторов.

4. Q: *Как работает отмена коммитов?*

   A: Четких инструкций нет, но рекомендуется использовать тип коммита `revert` и указание на хэши отменяемых коммитов:

   ```text
   revert(JIRATASK-123): отменены изменения коммитов 676104e, a215868
   ```

5. Q: *Что еще может предложить данное соглашение помимо упорядоченной истории коммитов?*

   A: Возможности для автоматизации, например:

   - автоматическая генерация осмысленного журнала изменений;
   - автоматическое определение семантического повышения версии (на основе _типов_ совершенных коммитов).
